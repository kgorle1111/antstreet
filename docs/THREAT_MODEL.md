# Threat model

What can go wrong in `boss`, what stops it, and the test that proves it. Every test named here is
checked to exist by `tests/test_threat_model.py`, so deleting a cited test breaks the build.

Scope: one investor on one machine, running `boss fund` (and `python -m boss.bench.run`) against
the headless `claude` CLI. Not in scope: multi-user machines, hosted use, untrusted ideas.

## Assets

| Asset | What it is | Where it is exposed |
|---|---|---|
| The user's machine and secrets | Files, environment variables, the CLI login, the network | The gate runs worker- and boss-written code; the worker CLI runs with the user's login |
| The user's money | Model spend on an API key or plan | Every slice and every boss call; the ledger holds estimates, not a bill |
| Integrity of "passed" | Only the gate says a check passed; rounds unlock, firing and the report depend on it | Anything that can change what the gate runs or reads |
| Integrity of the ledger and approval | The append-only record of spend and decisions; approval bound to content hashes | The run folder, the ledger writer, the approval check |

## Trust boundaries

| Party | Trusted to | Not trusted to | Where the line is drawn |
|---|---|---|---|
| Investor | Give the idea and budget; approve, reject, edit | Nothing is defended against the investor or their account | `approval.py`: only an `investor` event with matching hashes counts; `budget.is_top_up`: only an `investor` `topped_up` adds money or reopens a locked round |
| Boss model output | Propose tasks and check code | Money, ids, file names, paths; the check code is untrusted code | `boss.py` computes ids, names and money; `termsheet.py` validates; the investor reads every check |
| Role model output (`boss fund --roles`) | Advise or propose: a note, a proposed check, a demo script | Anything that changes the run by itself; its quotes, ids, file names and code | Each role's gate in code; `pipeline.py` shows its text only through the role's `render_*` function or `safe_text`; a proposal takes effect only on the investor's yes; the demo runs through the gate |
| Worker model output and files | Nothing | Its files (run by the gate), its status text, its notes | Gate copies files and decides; `handoff.py` quotes text; tools limited to `Read`, `Write`, `Edit` in one folder |
| The `claude` CLI | Enforce the tool whitelist, path rules and `--safe-mode` | Cost figures (client-side estimates), cap precision, login state | `worker.isolation_violations` reads its `system/init` event; `errors.py` classifies its result |
| The environment | The caller's shell, `PATH`, file permissions | Its variables reaching a child | `gate._env` and `worker.worker_env` are allowlists |

## Status key

- `controlled`: a mechanism exists and a test would fail if it broke.
- `partly controlled`: a mechanism and test exist, and what is left is stated.
- `accepted`: no complete control; the reason and what would change it are stated. Where possible a
  `test_accepted_risk_*` test pins the current limit, so lifting the limit fails the test and this
  file gets updated.

Everything else on the ledger (rulings, `resumed`, round approvals, costs, check results) is covered only by the unkeyed chain, so a forger who recomputes it can still write those. Not detected: lines dropped from the end of the file, an edit to the last line (nothing follows it yet), and a ledger with every `prev` removed, which reads as one from before the chain, so its unsigned approvals load; the approvals of a ledger written before this were never signed, so for them nothing is verified. Where no sandbox works (T39), code the gate runs can read the key, and anyone with the user's file access can (T29). Changes if run folders are shared or synced: refuse unchained ledgers, keep the key in a keychain, sign rulings and round approvals |

## Not covered

- The CLI's own behaviour (path rules, `--safe-mode`, budget cap) is verified by recorded probes,
  not by a test that calls the real CLI. A CLI upgrade can change it silently; `boss doctor` checks
  only the version and the login.
- API-key mode (`--bare`) is untested against the real CLI.
- The Linux (`bwrap`) sandbox: the argv is built and unit-tested but was never run (no `bwrap` on the
  machine it was written on). Treat Linux as unsandboxed until someone runs `docs/SANDBOX.md` step 1
  there.
- Prompt-injection resistance of the models themselves is not measured. The controls limit what an
  injected instruction can do (T18, T19), not whether the model obeys it.
